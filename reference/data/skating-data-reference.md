# 대한체육회 빙상 경기결과 시스템 — 리버스 엔지니어링 정리

`result.sports.or.kr/SK/` 를 파악하면서 확인된 사실 전부.
전부 실제 응답으로 검증된 내용이며, 추측은 별도 표기했다.

---

## 1. 시스템의 정체

### `.do` 는 파일이 아니다

자바 웹 프레임워크(Struts / Spring MVC 계열)의 관례다.
"`.do` 로 끝나는 주소가 오면 해당 컨트롤러를 실행하라"는 설정일 뿐,
서버에 그런 파일은 없다. 2000년대 초 자바 엔터프라이즈 스타일이고
한국 공공기관 사이트에 유독 많이 남아 있다.

### `INF###` 는 화면 ID

`INF` = information 계열, 뒤 숫자는 내부 화면 번호다.
번호 자체에 규칙적 의미는 없고, 5xx대와 7xx대는 서로 다른 시기·팀이
만든 화면 묶음으로 보인다(추정).

### API가 아니다

문서화된 계약이 없다. JSON이 아니라 HTML을 돌려주며,
파라미터 이름이 바뀌어도 아무도 공지하지 않는다.
로그인이 필요 없다는 의미에서 "공개"일 뿐,
이것을 긁는 행위는 스크래핑이지 API 사용이 아니다.

**따라서 언제든 깨진다고 가정하고 설계해야 한다.**
긁은 결과는 반드시 로컬에 저장하고, 매번 다시 긁지 않는 구조로 짠다.

## 3. 요청 규격

### 공통

```
POST https://result.sports.or.kr/SK/INF###.do
Content-Type: application/x-www-form-urlencoded
```

- **쿠키 불필요.** 세션 없이 단발 POST로 동작한다.
- 인코딩 **UTF-8**.
- User-Agent, Referer 불필요.
- 빈 값은 빈 문자열로 전송.

### 폼 필드 (`<form name="SearchVO">`)

```
classCd, toCd, pclassCd, eventCd, movSeq,
teamCd, idNo, pageIndex, searchKeyword
```

| 필드              | 의미        | 확인된 값            |
| ----------------- | ----------- | -------------------- |
| `pclassCd`        | 종목 코드   | `SK` (빙상)          |
| `idNo`            | 선수 ID     | 12자리               |
| `teamCd`          | 팀 코드     | `SK00445` (성남시청) |
| `pageIndex`       | 페이지      | INF703만 유효        |
| `searchKeyword`   | 검색어      | URL 인코딩된 한글    |
| `classCd`, `toCd` | 대회 식별자 | 미파악               |
| `movSeq`          | 영상 시퀀스 | 미파악               |

**`pclassCd=SK` 가 확장의 열쇠다.**
같은 시스템이 다른 종목 코드로 운영되고 있을 가능성이 매우 높다.
`result.sports.or.kr/GATE.do` 가 종목 선택 게이트웨이로 보인다(추정).

### 무시되는 파라미터

`pageUnit`, `recordCountPerPage` — eGovFrame 관례를 따를 것으로
기대했으나 실제로는 무시된다. 보내도 결과 개수가 동일했다.

## 4. 파싱 함정 전체 목록

실제로 겪은 순서대로. 다른 종목으로 확장할 때 그대로 재발한다.

### 4-1. `grep -c` 는 줄 수를 센다

등장 횟수가 아니다. 한 줄에 두 개 있으면 1로 센다.
`grep -o ... | wc -l` 을 써야 한다.

### 4-2. 타임스탬프 오염 ★

응답 하단에 이런 태그가 있다.

```html
<script src="/comn/front/js/com.js?v=1785426145197" defer></script>
```

13자리 밀리초 타임스탬프인데, `[0-9]{12}` 로 긁으면
앞 12자리(`178542679224`)가 idNo처럼 잘려 나온다.
**매 요청마다 값이 달라진다.**

이걸 모르고 스크래퍼를 돌리면 존재하지 않는 선수를
매일 하나씩 만들어낸다. 실제로 페이지 1·2·3에서
각각 다른 가짜 id가 하나씩 검출됐다.

→ **HTML 전체에 정규식을 던지지 말 것.**
구조로 먼저 좁히고(테이블 → 행 → onclick) 그 안에서만 패턴을 적용한다.

### 4-3. 문자열 개수 ≠ 행 개수

`fnPlayerHistory` 문자열이 21번 나오는데 실제 idNo는 10개였다.
원인 둘:

- `<script>` 안의 함수 정의 자체가 하나
- tablesaw 반응형 테이블이 PC용/모바일용 마크업을 중복 렌더링

### 4-4. 화면마다 idNo 위치가 다르다 ★

```html
<!-- INF701: 버튼에 -->
<td><button onclick="fnPlayerHistory(&#34;201105000916&#34;)">기록확인</button></td>

<!-- INF703: tr에, 버튼은 비어 있음 -->
<tr onclick="fnPlayerHistory(&#34;701318000150&#34;)">
  <td class="tac"><button onclick="fnPlayerHistory(&#34;&#34;)">기록확인</button></td>
</tr>
```

버튼만 보면 INF703에서 **0건**이 나온다.
`<tr>` 자신과 하위 요소의 onclick을 전부 수집하고 값이 있는 것을 채택해야 한다.

### 4-5. 빈 값이 정상적으로 존재한다

`fnPlayerHistory("")` 는 오류가 아니다. 버리지 말고 `idNo=None` 으로 보존.

### 4-6. HTML 엔티티

onclick 안 따옴표가 `&#34;` 로 인코딩돼 있다.
BeautifulSoup을 거치면 `"` 로 정규화되므로,
정규식은 따옴표를 옵셔널로 두는 것이 안전하다.

```python
r'fnPlayerHistory\(\s*["\']?(\d{6,})'
```

### 4-7. 자릿수를 12로 고정하지 말 것

관측된 idNo 체계가 최소 셋이다 (5절 참조).

### 4-8. 표시 건수를 신뢰하지 말 것 ★

"남윤창" 검색 기준:

| 값                       | 숫자 |
| ------------------------ | ---- |
| 화면 표시 "선수 정보(N)" | 13   |
| 실제 행 수               | 23   |
| 고유 idNo                | 2    |

셋 다 다르다. 집계 단위가 서로 다른 것으로 보이나 정확한 기준은 불명.
**루프 종료 조건이나 검증 실패 판정에 절대 쓰지 말 것.**

### 4-9. 페이지 간 중복 + 정렬 불안정 ★

INF703에서 같은 (소속, 종별) 조합이 1·2·3 페이지에 모두 등장하고,
2페이지 안에서 같은 행이 두 번 나오기도 했다.
서버 쿼리의 `ORDER BY` 가 유일하지 않은 컬럼인 것으로 보인다.

→ 종료 조건을 "새로운 행이 없으면 중단"으로 하면 안 된다.
중복만 가득한 페이지가 정상적으로 존재한다.
**"파싱된 행이 0개면 중단"** 하나만 쓴다.

### 4-10. onclick 문자열 비교는 무의미

같은 선수면 소속이 달라도 onclick이 글자 하나까지 같다.
`diff` 로 페이지를 비교하면 "동일"이 나오지만 실제 내용은 다르다.
중복 판정 키는 반드시 **(idNo, 소속, 종별)** 튜플.

### 4-11. INF503은 테이블이 2개 ★

```
table 0: caption="최종등록정보"  (4행)
table 1: caption="대회참가이력"  (275행)
```

인덱스로 고르면 4행짜리 등록정보를 데이터로 착각한다.
**반드시 `caption` 텍스트로 선택.**

### 4-12. `diff` 로 응답 동일성을 판정할 때

타임스탬프(4-2) 때문에 항상 "다름"이 나온다.
제거하고 비교해야 한다.

```bash
diff <(sed 's/[0-9]\{13\}//g' h1.html) <(sed 's/[0-9]\{13\}//g' h2.html)
```

## 6. 데이터 모델

### 6-1. idNo 체계가 최소 3종

| 형식             | 예시                                         | 해석                     |
| ---------------- | -------------------------------------------- | ------------------------ |
| `YYYYMM` + 6자리 | `200604009460`, `201105000916`               | 최초 등록 연월. 주 체계  |
| `98####` + 6자리 | `981618000141`, `981718000443`               | 구 체계 추정. 전부 1~2행 |
| `70####` + 6자리 | `701318000131`, `...142`, `...150`, `...155` | **연번.** 일괄 등록 사고 |

`70131800xx` 는 이규호·신동민·남윤창·이동현에게서 연속 번호로 나왔다.
같은 대회 참가자 명단을 한 번에 등록하다 생긴 뭉치로 보인다.

→ 접두사로 필터링하지 말 것. **행 수와 소속 일치로 판별**해야
다른 종목·다른 시기의 유사 사고도 자동으로 잡힌다.

### 6-2. 고아 레코드 — 학교명 미정규화 ★

```
201105000916  남윤창  달산초등학교  남자초등3,4학년  대구   (정상, 22행)
701318000150  남윤창  달산초        남자초등3,4학년  대구   (고아, 1행)
```

같은 학교인데 표기가 달라 별도 선수로 등록됐다.
고아 id의 기록은 2013-10-12~13 이틀치뿐이고,
정상 id에 같은 소속·종별이 이미 들어 있다.

**같은 사고가 이규호·신동민·이동현에게도 있다.**
서비스로 만들려면 학교명 정규화 사전이 필요하다.

### 6-3. 한 idNo가 전 커리어를 커버한다 ★

프로젝트의 핵심 가정이었고 검증됐다.

```
201105000916 = 대구신천초 → 달산초 → 경신중 → 칠성고
               → 한국체대 → 경희사이버대
```

초등학교 저학년부터 대학까지 하나의 id로 이어진다.
현재 idNo로 유년기 기록을 조회할 수 있다.

### 6-4. 한 선수가 여러 행으로 나온다

검색 결과는 **선수 단위가 아니라 (선수 × 소속 × 종별) 등록 이력 단위**다.
남윤창 한 명이 23행. 반드시 idNo로 묶어야 한다.

### 6-5. 동명이인이 실재한다

박지원은 2026/27 국가대표 명단에만 둘이다 (여자 전북도청 / 남자 서울시청).
행 수만으로 자르면 실제 인물을 놓친다.
**소속 + 성별** 두 축으로 판별해야 한다.

박지원 검색 결과 9개 후보 중 행 수 1위(28행)가 남자,
2위(19행)가 국대 여자 박지원이었다.

### 6-6. 최종등록정보 테이블의 값

```
이름 / 성별 / 출생년도 / 종별 / 소속팀 / 시도
```

- **출생년도가 있다.** "1998년" 형태. 나이 기반 분석의 근거.
- 소속팀은 `성남시청 (SK00445)` 형태 → 팀명과 팀코드로 분리 가능.
- key-value 레이아웃이므로 인덱스 접근 금지, 셀 순서대로 쌍 파싱.

## 7. 도메인 규칙 — 데이터를 잘못 읽는 방법들

### 7-1. 순위는 라운드 안에서의 등수다 ★★

가장 위험한 함정. 최민정 2007 초등부 500M:

```
예선5조     52.55  2위
준준결승3조  51.12  2위
준결승2조   51.20  5위
채점종합    51.20  9위   ← 실제 성적
```

순위 컬럼을 무차별 평균하면 4.5위, 실제는 9위.
**성적을 논할 때는 `채점종합` > `결승` 순으로 단 하나만 채택.**
예선·준결승·준준결승은 제외.

### 7-2. 결승이 예선보다 느린 것은 정상이다 ★★

쇼트트랙은 레인 없는 착순 경기다. 결승에서 전술적으로
천천히 타다 막판에 붙는다.

```
김길리 1500m 초등: 예선 143.040 → 결승 178.132 (결승 1위)
최민정 1500m 오픈: 예선 157.060 → 결승 192.951 (결승 1위)
```

"결승이 예선보다 느림"을 이상치로 잡으면
214건 중 대다수가 1위 기록인 오탐이 된다.

→ **기록(시간) 기반 분석에는 예선 기록만 쓴다.**
→ **순위 기반 분석에는 채점종합/결승을 쓴다.**
→ 이 종목에서 기록으로 실력을 비교하는 것 자체가 부적절하다.

### 7-3. `1500M` 과 `1500M S.F` 는 별개 경기

슈퍼파이널. 같은 날 두 번 탄다.

```
20210509  1500M      결승Final  02:21.700  2위
20210509  1500M S.F  결승Final  02:23.077  1위
```

거리를 1500으로 뭉개면 그룹핑 키가 겹쳐 중복이 남는다.
실제로 56건이 이 문제였고, 전부 1500m였다.

### 7-4. `결승B` 는 하위 결승

결승B 1위는 전체 상위권이 아니다. 별도 표시 필요.

### 7-5. 일자가 `-` 인 행 ★

`채점종합` 라운드는 특정 일자가 없어 `-` 로 들어온다.
연도 파싱이 실패해 NaN이 되고, 학령구간은 종별에서 파생되므로
살아남아 **같은 성적이 두 번 집계된다.**

전국동계체육대회 회차 → 연도로 복원 가능:

```
연도 = 회차 - 88 + 2007
제88회=2007 … 제94회=2013 … 제100회=2019 … 제107회=2026
(제89·102·106회는 미개최 또는 데이터 없음)
```

### 7-6. 유사한 대회명이 실재한다

```
제30회 전국남녀 쇼트트랙 스피드스케이팅대회
제30회 전국남녀 종별 종합 쇼트트랙 스피드스케이팅 선수권대회
```

회차만으로 묶으면 안 된다. 대회명 전체 문자열로 구분.

### 7-7. 기록 형식이 여러 가지

```
"00:43.121" → 43.121
"01:34.394" → 94.394
"2:58.30"   → 178.30    (0 패딩 없음)
"51.12"     → 51.12     (분 없음)
"05:06.73"  → 306.73
""          → None
```

정규식 하나로 처리하지 말고 콜론 개수로 분기.

### 7-8. 종별 값 목록

```
{성별}초등1,2학년 / 초등3,4학년 / 초등5,6학년 / 초등부
{성별}중학부 / 고등부 / 대학부 / 일반부
{성별}부                              ← 연령 무관 오픈 경기
```

`여자부` / `남자부` 는 오픈이므로 학령 분석에서 제외해야 한다.

### 7-9. 나이 계산의 한계

출생 연도만 있고 생월일이 없다.
`나이 = 대회연도 - 출생년도` 는 만 나이보다 최대 1살 높고,
**동계 대회가 1~2월에 몰려 있어 체계적으로 +1 편향**이 있다.

## 8. 데이터 커버리지

연도별 기록 건수 (국가대표 14명 기준):

```
2007:  20    2012: 154    2017: 351
2008:  18    2013: 137    2018: 385
2009:  19    2014: 282    2019: 420
2010:  28    2015: 288    2020: 130  ← 코로나
2011:  34    2016: 355    2021: 408
```

**2012년에 5배로 뛴다.** 그 이전은 전산화가 부분적이고,
전국동계체육대회 같은 큰 대회만 남아 있다.

→ 1990년대 중반 이전 출생 선수는 유년기 기록이 통째로 비어 있다.
노아름(1991년생)의 초등부 기록 0건은 "출전하지 않음"이 아니라
"기록이 없음"이다. **이 둘을 구분할 수 없다는 점을 명시해야 한다.**

신뢰도 판정 기준:

```
초등 6학년 추정연도 = 출생년도 + 12
  >= 2014  → high
  2012~13  → medium
  <  2012  → low
```

## 9. 검색 기능을 만들려면 — 열거 문제

현재 방식은 **이름을 알아야 찾을 수 있다.**
서비스로 만들려면 전체 선수 목록이 필요한데, 그 방법이 아직 없다.

### 시도할 수 있는 경로

**A. 대회 결과에서 역으로 수집 (가장 유망)**

`INF201` (일정/결과) → `INF202` (대회 상세) → 참가자 전원.
모든 대회를 순회하면 그 대회에 출전한 모든 선수가 나온다.
경기 기록이 있는 선수는 반드시 어떤 대회에든 나타나므로
이론상 전수 수집이 가능하다.

→ `INF202` 의 `classCd`, `toCd` 파라미터 구조를 먼저 까야 한다.
`fnEventInfo(classCd, toCd, searchAppYn)` 시그니처는 이미 확보.

**B. 팀 → 소속 선수**

`INF702` (팀 검색) → `INF501` (팀 기록, `fnTeamRecord(teamCd)`).
팀 페이지가 소속 선수 명단을 보여준다면 팀을 순회해 수집.
팀 코드 형식 `SK00445` 확인됨.

→ INF501 응답 구조 확인 필요. 미탐색.

**C. 성씨 × 흔한 이름 조합 완전 탐색**

무식하지만 확실하다. 다만 요청 수가 수천 건이 되고
서버에 부담이며 누락 가능성이 남는다. 최후의 수단.

### 열거 후에 필요한 것

1. **로컬 인덱스** — 검색이 남의 서버를 때리지 않도록
   (name, idNo, 소속목록, 성별, 출생년도) 를 미리 구축
2. **학교명 정규화 사전** — "달산초" = "달산초등학교"
3. **고아 id 병합 규칙** — 이름+성별+지역+종별이 같고
   기록이 겹치지 않으면 동일인으로 병합 후보
4. **동명이인 분리** — 소속 + 성별 + 출생년도

### 참고 규모

대한체육회 등록 기준 쇼트트랙 선수는 **2,907명**.
전수 수집 시 요청 간격 1초로 잡으면 약 50분.
등록 선수만 세는 숫자이므로 실제 기록 보유자는 이보다 많다.

## 11. 다른 종목으로 확장할 때

`result.sports.or.kr` 은 대한체육회 통합 시스템이다.
`/SK/` 는 빙상 경로이고, 같은 구조가 다른 종목에도 있을 가능성이 높다.

먼저 확인할 것:

1. `result.sports.or.kr/GATE.do` — 종목 선택 게이트웨이로 추정
2. 다른 종목 경로에서 `INF703`, `INF503` 이 같은 파라미터로 동작하는지
3. 응답 HTML 구조가 동일한지 (같은 템플릿을 쓴다면 파서 재사용 가능)

**위 4·6·7절의 함정 대부분은 시스템 공통일 가능성이 크다.**
특히 타임스탬프 오염(4-2), 테이블 caption 선택(4-11),
`-` 일자 중복(7-5)은 템플릿 레벨 문제로 보인다.

반면 7절의 도메인 규칙(라운드 위계, 전술적 페이스 조절, 슈퍼파이널)은
쇼트트랙 고유다. 종목마다 새로 파악해야 한다.
